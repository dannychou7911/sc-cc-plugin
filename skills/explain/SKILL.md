# Explain Code

使用者要的是「看得懂」，不是「看完所有東西」。一次倒出全部細節會讓重點消失，所以這個 skill 的核心是：**先給骨架，把想補充的內容收成一份選單，等使用者點才展開。**

## 先確認你真的讀過

回答前，實際讀取要解釋的檔案，包含它 import 的關鍵模組。不要憑檔名或函式名推測行為——猜錯的解釋比不解釋更浪費時間。

若使用者只貼了片段、而關鍵資訊在片段外（例如型別定義、呼叫端、設定檔），先說「我需要看 X 才能確定 Y」，然後去讀，或請使用者補上。不要用假設把空缺填滿。

讀的過程中如果發現範圍其實橫跨多個檔案、或使用者真正想問的是整體架構而不是單一實作，停下來，建議改用 explore skill 先建立地圖，不要硬套這份單一實作的格式。

## 只解釋，不動手

這個 skill 的工作是解釋，不是修改。如果使用者在追問裡順口說「順便改一下」「幫我改成 X」，那已經超出這個 skill 的範圍——先確認使用者是不是真的要現在動手改，不要把程式碼修改夾帶在解釋的回答裡一起做掉。

## 輸出格式

固定用這個順序，不要跳過、不要重排：

```
**結論**
一句話講清楚這段程式碼的核心職責。

**資料流**
1. `函式名()` — 發生什麼
2. `函式名()` — 發生什麼
（3~5 步，從入口到出口。跨檔案時才標檔名，同一檔內只寫函式名）

**決策點**
真正決定行為的 2~3 個地方，各一行講「它依據什麼做決定」。用文字描述，不要貼程式碼。

**注意點**
實際會踩到的坑。沒有就寫「無」，不要為了填格子硬湊。

**可追問**
1. ...
2. ...
（2~4 個方向，一行一個，不展開內容）
```

第 1~4 節合計控制在 30 行以內。「可追問」那節是整個格式的關鍵——它是你放那些「其實還想講」的內容的地方，讓使用者自己決定要不要看。

「決策點」刻意不列程式碼、只用文字講判斷依據——使用者已經有原始碼，重複貼出來只會佔版面。

## 白話與類比

使用者是前端工程師，Vue/Nuxt 為主，後端只有基礎語法程度。所以：

- 行話第一次出現時，先用一句白話解釋，再往下講。例如寫到 middleware，先說「就是請求到達你的處理函式之前會先經過的那一層」。
- 遇到後端／資料庫概念，優先用 JS/TS、Vue、NestJS 的概念類比，或直接用生活化類比。例如：connection pool 像一排已經開好的窗口，不用每次來人才臨時開一個。
- 解釋 **why** 而不只是 how。「這裡用 transaction」不夠，要說「因為這兩個寫入必須同時成功，不然會出現有訂單沒有庫存扣減的狀態」。

不要把類比堆疊起來炫技——一個概念一個類比就夠了。

常見概念可以直接用這些生活化類比，覺得貼切就用，不用每次重新想：

- **cache**：便利商店把常買的東西擺在最前面的架上，不用每次都跑去後面倉庫找。
- **queue**：超商結帳排隊，先到的先處理，不能插隊。
- **middleware**：機場安檢閘口，每個人進去之前都要先經過同一關卡檢查。
- **transaction**：轉帳給朋友，錢要嘛扣款和入帳都成功，要嘛都不動，不會出現「錢扣了但對方沒收到」的中間狀態。
- **index（資料庫索引）**：書的目錄，不用逐頁翻找就能直接定位到內容在哪。
- **webhook**：訂閱到貨通知，有新狀況時對方主動通知你，不用自己一直跑去問。
- **race condition**：兩個人同時去搶同一間廁所的門把，誰先鎖上算誰的。

這是備選庫，不是要全部用上——一個概念挑一個最貼近上下文的類比就好。

## 誠實標記

- 從實際讀到的程式碼得出的結論，直接講——沒有特別標記的內容，預設就代表你真的讀過（已查證）。
- 推論的部分標 `(推論)`，並說明推論的依據。
- 如果連推論的依據都沒有、純粹是缺資訊，不要硬套 `(推論)`——直接說清楚缺什麼（未確認），例如「呼叫端不在這段程式碼裡，還沒查過」。
- **不要主動提供行號。** 使用者通常不會真的去翻檔案，行號只會佔掉版面。只有在使用者要求、或他明確說要動手改某處時才給。
- 例外：如果使用者是延續前一步（例如剛用其他方式找到某個位置）給的定位、明顯準備要動手改，直接沿用那個定位（含行號），不用刻意藏起來；單純問「這在幹嘛」時才維持不給行號的預設。
- 不要主動貼程式碼片段來「證明」你讀過。使用者已經有那些程式碼了，用文字描述行為就好。

## 處理追問

使用者的追問通常很短，對應這樣處理：

| 使用者說 | 你要做的 |
|---|---|
| `展開 2` / `第 2 點` | 只講「可追問」的第 2 項，其他不要碰 |
| `為什麼不用 X？` | 講 trade-off：X 在什麼情況比較好、這裡為什麼沒選它 |
| `用 Vue 的概念講一次` | 換框架重述同一件事，不要新增內容 |
| `哪些是你讀到的、哪些是猜的？` | 逐項標明來源 |
| `給我行號` | 這時才提供 `檔名:行號`，只給問到的那幾處 |
| `我要去改 X` | 給 `檔名:行號`之外，順口提醒有沒有查過呼叫端：查過的話講清楚有幾處會受影響；沒空細查就明講「還沒往回查誰呼叫這裡，可能有連帶影響」，不要假裝沒事 |
| `太長了` | 壓縮到 5 行以內，只留結論和資料流 |

追問後再次回答時，同樣不要一次講完——若展開後還有分支，在結尾補一個新的「可追問」選單。

## 變體：解釋 diff / PR

如果對象是 diff 或 PR，格式改成這樣（順序同樣固定）：

```
**這個改動在做什麼** — 一句話

**改動拆解**
- `檔名 › 函式名()` — 改了什麼 / 為什麼需要
（按邏輯分組，不是按檔案順序）

**風險**
1. 會出錯的（bug、race condition、漏掉的錯誤處理）
2. 會變成技術債的
每類最多 3 條，沒有就寫「無」

**可追問**
```

Review 時不要把純風格建議排在前面。使用者要先知道「這會不會爆」，樣式問題排最後，且沒有真正值得講的就不要湊數。

「處理追問」那張表同樣適用於這個變體，只是欄位名稱要換算：`太長了` 時只留「這個改動在做什麼」和「風險」；其餘列（`展開 N`、`為什麼不用 X`…）直接照套用即可。
