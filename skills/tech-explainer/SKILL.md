# Tech Explainer

給特定讀者產生技術說明文件。整份 skill 圍繞兩個判斷：**這位讀者已經知道什麼**（決定解釋到多細、能不能放程式碼），以及**文件會被貼到哪**（決定能用什麼語法）。判斷錯了，再漂亮的結構都救不回來。

## Step 1：定位讀者與載體

不要為了流程而問。能從對話脈絡推斷的就直接推斷，並把假設寫在文件開頭（模板的「閱讀對象」區塊），讓使用者一眼看到猜錯了可以糾正 —— 這比先問三個問題再開工快得多。

| 項目 | 怎麼推斷 | 推不出來時的預設 |
|------|---------|----------------|
| 讀者背景 | 使用者說「給 PM / 新人 / 後端」就照那個 | 讀者是使用者自己：前端工程師，對後端/DB 生疏 |
| 主題 | 當前對話正在處理的變更、使用者指的檔案或概念 | **問**（這個不能猜） |
| 載體格式 | 提到 Obsidian → Obsidian；提到 MR / GitHub → GFM；「貼給某人看」→ 純文字 | 對話內 Markdown |

只有在讀者背景完全不明、而且深淺差異大到會寫出兩份完全不同的文件時，才值得停下來問。

## Step 2：蒐集事實 —— 不可跳過

說明文件的讀者通常**沒有能力發現錯誤**。對新手來說，一個編錯的方法名或顛倒的流程順序會直接變成他的心智模型，而且他會相信很久、拿去跟別人講。所以文件裡的每個具體事實都要來自實際讀過的來源，不能來自印象。

| 主題類型 | 動筆前必須先做 |
|---------|--------------|
| 程式碼變更 | `git diff`（或使用者指定的 commit range）→ 讀受影響檔案的完整內容，不只讀 diff 片段 |
| 現有架構 / 模組 | Grep/Glob 找入口 → 讀主要檔案與它的呼叫鏈 |
| 第三方框架 / 工具機制 | 查官方文件（context7 或 WebFetch）；版本行為不確定就查，不要憑記憶 |
| 純概念（HTTP、race condition…） | 不需讀 code，但類比必須站得住腳 |

三條規則：

- 程式碼片段從檔案複製，附 `path:line`，讓讀者能自己去看上下文
- 查不到或無法確認的，標 `> [!warning] 待確認` 交給使用者補，**不要編一個看起來合理的**
- 推測要標明是推測（「我的理解是…，沒有驗證過」），別讓它混在事實裡

## Step 3：選深度與篇幅

讀者是否會去讀 code，決定內容形態：

| 讀者 | 放程式碼？ | 重點放哪 |
|------|-----------|---------|
| 工程師（熟這個領域） | 可以，只放關鍵幾行 | 取捨、反直覺決策、坑 |
| 工程師（這個領域的新手） | 可以，但每段都要類比橋接 | 建立心智模型，一次只引入一個新概念 |
| PM / QA / 主管 | 不放 | 輸入輸出、影響範圍、失敗時使用者看到什麼 |

篇幅選**最小可用**的那一檔。過長的說明文件沒人讀完，三句話講清楚勝過五章沒人看：

| 檔次 | 何時用 | 形態 |
|------|-------|------|
| 速解 | 單一概念、單一疑問 | 對話內 150–300 字：一個類比 + 一句 why，不編章節 |
| 說明文件（預設） | 一個模組、一次變更、一段架構 | 完整模板 |
| Walkthrough | 對方要照著操作（交接、onboarding） | 說明文件 + 可執行步驟 + 怎麼確認成功 |

## Step 4：套用六項原則產生文件

見 [principles.md](references/principles.md) —— **產生文件前必須讀**。六項原則依序是：讀者知識邊界、Why→What→How、類比橋接、圖解流程、解釋反直覺決策、分層資訊。章節結構用該檔末尾的模板（速解不用模板）。

## Step 5：輸出

| 載體 | 做法 |
|------|------|
| Obsidian | 呼叫 `sc-cc-plugin:obsidian-markdown` skill（plugin 提供的 skill 要帶 plugin 前綴才叫得到）。該 skill 不在時，自行依 Obsidian 語法寫檔並確認存放路徑 |
| MR / GitHub / GitLab | Callout 換成 GFM 支援的類型（見原則六），其餘照模板 |
| 純文字 / Slack / Confluence | Callout 降級為粗體標籤行，Mermaid 改為文字流程（`A → B → C`） |
| 對話內 | 直接輸出 Markdown |

## 交付前自檢

四題，任一題答不出來就回去補：

1. 讀者不熟的詞，第一次出現時都有橋接或白話解釋嗎？
2. 每個「看起來很怪」的寫法，都寫了為什麼嗎？
3. 文件裡的檔名、方法名、流程順序，都來自我實際讀過的內容嗎？
4. 一個只讀標題 + warning 的人，抓到重點了嗎？
