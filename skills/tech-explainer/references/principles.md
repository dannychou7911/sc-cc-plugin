# 六項說明原則

這六項是手段，目的只有一個：讓這位特定讀者真的看懂，而不是讓文件看起來很完整。

---

## 原則一：先確認讀者知識邊界

動筆前劃出兩條線：

- **已知（不用解釋）**：讀者日常接觸的概念
- **未知（必須解釋）**：領域陌生詞、縮寫、隱性假設

範例：對象是「前端 2-3 年經驗、NestJS 新手」

| 已知（可直接用） | 未知（需先解釋） |
|-----------------|-----------------|
| HTTP 請求、元件生命週期、Vue | Guard、Module、DI |
| async/await、型別 | `@Injectable()`、`ExecutionContext` |

這兩欄不只決定「要解釋什麼」，也決定原則三的類比從哪裡取材。

> 說明最常見的失敗原因：「作者忘記自己曾經是新手。」

---

## 原則二：Why → What → How 順序

永遠從「為什麼需要它」開始，不要從功能描述開始。讀者沒有問題意識時，功能描述只是一串無處可掛的名詞。

```
Why：這東西解決了什麼問題？不用它會怎樣？
What：整體長什麼樣子？（用圖先建立全貌）
How：每個部分怎麼運作？
```

反例（錯誤順序）：
> ❌「WebhookSecretGuard 實作了 CanActivate 介面，在 canActivate() 中驗證 header...」

正確順序：
> ✅「任何人都可以打你的 webhook URL，所以需要一個守門員驗證請求真的來自 Telegram。這個守門員就是 WebhookSecretGuard...」

---

## 原則三：類比橋接

每次引入讀者不熟悉的概念，先找一個他**已知的東西**做橋。

類比公式：`[新概念] 就像 [已知概念]，差別是 [關鍵差異]`

「差別是」這半句不能省。只講「像什麼」，讀者會把舊概念的預期整包搬過來，日後撞到差異處比沒有類比更困惑。

類比要從**這位讀者的日常**取材，不要從清單裡挑。同一個 NestJS Guard：對前端工程師講「Vue Router 的 `beforeEnter`」、對 QA 講「進場前的門票查驗」、對 Java 後端直接講「Servlet Filter」。所以先看原則一畫出的「已知」欄，再造類比。

三個示範（示範的是公式，不是可選清單）：

- **Guard** → 像 Vue Router 的 `beforeEnter`，決定放不放行；差別是它在 server 端，擋的是 HTTP 請求而不是頁面切換
- **`OnModuleInit`** → 像 Vue 的 `mounted()`；差別是它在整個服務啟動時跑一次，不是每個實例各跑一次
- **Webhook** → 像外賣送達時店家打電話通知你，而不是你每分鐘打去問到了沒

## 原則四：圖解流程

選最適合的圖表類型：

| 情境 | 圖表類型 | Mermaid 語法 |
|------|---------|-------------|
| 誰跟誰說話、訊息順序 | Sequence Diagram | `sequenceDiagram` |
| 決策分支、條件判斷 | Flowchart | `flowchart TD` |
| 系統組成、模組關係 | Architecture Graph | `graph TB` |
| 新舊對比 | 並排 Graph | 兩個 `subgraph` |

規則：**圖負責讓人看懂整體，文字負責解釋為什麼這樣設計。** 兩者只能選一時，優先給圖。

實務注意：節點標籤含 `()`、`:`、`|`、`#` 會讓 Mermaid render 失敗，用引號包住標籤即可 —— `A["驗證 secret (X-Telegram-Bot-Api-Secret-Token)"]`。混用中英標點時一律加引號最省事。需要 class diagram、ER、狀態機這類更複雜的圖，或要把圖轉成圖片檔，交給 `design-doc-mermaid` skill。

## 原則五：解釋反直覺的決策

程式碼裡最讓新手困惑的不是「這行做什麼」，而是「**為什麼要這樣做**」。前者他自己讀得出來，後者只存在寫的人腦裡 —— 那才是文件真正的價值。

遇到以下任一情況，補上原因：

- 用了不常見的 API 或模式
- 捨棄了「更直覺」的做法
- 看起來像 bug 但其實是刻意的
- 有安全考量（如 `timingSafeEqual` vs `===`）
- 有框架限制（如 ValidationPipe 導致不能用 `@Body()`）

格式建議：

```markdown
> [!warning] 為什麼永遠回 200？
> 因為 Telegram 規則：非 2xx 回應 → Telegram 不斷重試 → 被洪水請求淹沒。
```

---

## 原則六：分層資訊（必讀 vs 選讀）

用 Callout 幫讀者篩選資訊密度。目標：讀者「只讀標題 + warning」就抓得住重點，有興趣再深讀。

| Callout 類型 | 使用時機 |
|-------------|---------|
| `[!info]` | 背景知識、可跳過的補充 |
| `[!tip]` | 給讀者背景的友善橋接（如「給前端工程師的類比」） |
| `[!warning]` | 搞錯會壞事的關鍵點 |
| `[!caution]` | 要注意但不致命的事 |
| `[!note]` | 一般補充說明 |

**Callout 語法會隨載體改變。** 用錯不會壞掉，只會 render 成一塊灰色引用 —— 但那正好抹平了你想做的分層，所以要先確認載體：

| 載體 | 可用語法 |
|------|---------|
| Obsidian | 上表五種都支援，還可加 `-` 做預設折疊（`> [!info]-`） |
| GitHub / GitLab（GFM） | 只支援 `[!NOTE]` `[!TIP]` `[!IMPORTANT]` `[!WARNING]` `[!CAUTION]`，**沒有 `[!info]`** —— 用 `[!NOTE]` 代替，並照官方寫法用大寫 |
| 純文字 / Slack / Confluence | 沒有 Callout。降級為一行粗體標籤：`**⚠️ 為什麼永遠回 200？** 因為…` |

## 文件結構模板

「說明文件」與「Walkthrough」用這個結構；速解不編章節，直接寫。

節次不是硬規定：沒有反直覺決策就不要硬湊、不是解釋程式碼變更就砍掉變更摘要。硬撐出來的空章節比少一節更傷可信度。

```markdown
# [主題]

> [!info] 閱讀對象
> 針對 [讀者背景] 撰寫，假設你已經知道 [已知清單]。

## 1. 為什麼需要它？（Why）
[問題描述 + 不用它的後果]

## 2. 整體樣子（What）
[Mermaid 圖建立全貌]

## 3. 每個部分怎麼運作（How）
### 3.1 [元件 A]
> [!tip] 給 [讀者身分] 的類比
> [新概念] 就像 [已知概念]，差別是 [關鍵差異]

[程式碼片段，附 `path:line`]

> [!warning] 為什麼不用更直覺的 X？
> [原則五：反直覺決策的原因]

### 3.2 [元件 B]
...

## 4. 實際操作步驟（若讀者需要照著做）
[指令、環境變數、以及怎麼確認做成功了]

## 5. 變更摘要（若在解釋程式碼修改）
| 檔案 | 動了什麼 | 為什麼 |
|------|---------|--------|
```

**讀者不讀 code 時（PM / QA / 主管）改兩處**：第 3 節從「元件怎麼運作」換成「哪些流程受影響」，用「輸入 → 輸出」和「正常流程 vs 失敗流程」描述，不放程式碼；第 5 節換成「使用者或測試會看到什麼差異」。
