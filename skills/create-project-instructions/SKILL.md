# Create Project Instructions

為目前 repository 產生精簡、可執行、可驗證的專案級 `CLAUDE.md` 或 `AGENTS.md`。只寫會改變代理判斷與行動的專案知識，不把指令檔寫成 README、教學、規格或單次任務清單。

## 執行邊界

- 產生內容不代表可以修改 repository；只有使用者明確要求建立、寫入或重寫檔案時才可落盤。
- 未經授權不得修改程式碼、設定、依賴、文件、Git 狀態或外部系統。
- 不得虛構命令、路徑、版本、架構、團隊流程或工具能力。
- 缺少證據的候選規則列入「待確認」，不得寫入正式規則。
- 更新既有檔案時保留仍有效的規則，只移除有證據支持為錯誤、重複、過期或位置不當的內容。
- 若 repository 已有同名檔案，先審閱再更新，不直接覆蓋。

## 先決定目標檔案

依使用者指定建立 `CLAUDE.md` 或 `AGENTS.md`。未指定時，以 repository 已存在且實際使用的指令檔格式為準；兩者都不存在且無法從工具或專案慣例判定時，只產生建議稿並標示檔名尚待決定。

不要假設兩種工具具有相同的檔案探索、作用域、覆蓋或命令機制。若規則依賴特定代理功能，明確標示適用工具；共用規則應寫成不依賴特定 slash command 或隱含能力的形式。

## Repository 探索

先找出真正會影響指令內容的證據，避免無目的地遍歷全部檔案。

### 必查來源

1. 現有的 `AGENTS.md`、`CLAUDE.md` 與巢狀指令檔：確認既有規則、作用域與衝突。
2. `README`、開發文件與架構文件：理解專案用途、啟動方式與已記錄決策。
3. package manifest、lockfile、runtime 與 workspace 設定：確認語言、framework、版本來源、套件管理器與 scripts。
4. lint、format、typecheck、test、build 與 CI 設定：確認可執行命令及已由工具強制的規則。
5. 主要目錄、入口點與少量代表性檔案：確認分層、命名、依賴方向與實際慣例。
6. Git hooks、generator、codegen 與專案 script：確認修改後必須同步或禁止手改的產物。

### 按需查證

- 涉及 API、認證、資料庫、部署、安全或文件 SOT 時，讀取對應設定與權威文件。
- 涉及特定子系統時，只抽查該子系統足以確認規則的代表性檔案。
- 說法來自單一實作案例時，不得直接提升為全專案規則；先確認是否有工具、文件或多個一致案例支持。

## 證據分類

建立規則前，將發現分為：

- 已查證事實：可由設定、文件、命令、目錄或一致實作證明。
- 明確約束：由使用者、權威規格、ADR、CI 或 hook 明確要求。
- 現有慣例：多個代表性實作一致，但沒有強制工具保證。
- 推論：根據有限證據推測，不能直接寫成規則。
- 待確認：來源衝突、缺少檔案、命令不可執行或需要使用者裁定。

規則必須能追溯至前三類之一。若文件、測試、設定與程式碼互相衝突，列出衝突，不自行挑選答案。

## 規則收錄標準

每個候選項目都必須通過下列檢查：

1. 必要性：移除後是否會增加錯誤修改或錯誤判斷的機率。
2. 專案性：是否為本 repository 特有，而非通用工程常識或個人回覆偏好。
3. 可執行性：代理能否明確知道要做什麼、不得做什麼或何時停止。
4. 作用域：適用目錄、檔案、任務與例外是否清楚。
5. 可驗證性：能否由命令、測試、檔案或明確條件確認。
6. 穩定性：是否避免容易過期的人數、檔案數量、暫時狀態或重複版本資訊。
7. 唯一性：是否已由 formatter、linter、CI、README、spec 或更接近的指令檔充分管理。
8. 權限一致性：是否把「必須分析」誤寫成「可以自行修改、commit、push 或操作外部系統」。

未通過的內容不要硬塞進指令檔：通用偏好移到全域規則，業務需求移到 spec，教學移到 `docs/`，單次需求留在任務提示詞。

## 規則撰寫方式

- 使用直接、可觀察的行為描述，避免「注意品質」「妥善處理」「遵循最佳實務」等空泛要求。
- 需要絕對禁止時才使用 `MUST` 或「不得」；主要用於安全、相容性、資料完整性、架構邊界與明確授權限制。
- 預設慣例應允許有理由的例外，並說明何時需要回報或取得裁定。
- 命令使用 repository 內實際存在的 script，不依照框架慣例自行補齊。
- 版本已有 manifest 或 lockfile 作為權威來源時，優先指向來源；只保留真正影響相容性的限制。
- 不寫短期盤點數字，例如元件數、測試數或目前暫無某目錄。
- 詳細流程、案例或長篇領域知識放入既有 `docs/`，主檔只保留入口、使用時機與不可違反條件。
- 同一規則只出現一次；規則之間衝突時先處理優先順序。

## 建議內容結構

不要機械產生所有章節。只有證據支持且會影響代理工作時才加入。

### Project Context

說明專案用途、核心使用者或不能破壞的業務限制。README 已充分說明且不影響判斷時可省略或只放連結。

### Sources of Truth

列出規格、ADR、API schema、產生型別或其他權威來源，並定義來源衝突時的處理方式。不要直接假設測試或現有程式碼必然高於規格。

### Tech Constraints

只記錄會影響實作選擇的 runtime、framework、語言模式、套件管理器、相容性與禁止升級事項。完整依賴版本交由 manifest 與 lockfile 管理。

### Repository Structure

記錄重要目錄責任、模組邊界、依賴方向、生成檔案與禁止手改區域，不逐一列出可由目錄樹直接看懂的檔案。

### Architecture and Coding Rules

記錄專案特有的資料流、分層、元件選擇、DTO、狀態管理、樣式、命名與例外。formatter 或 linter 已完全強制的格式規則不重複。

### Change Boundaries

區分可直接修改、需先確認與不得修改的範圍。明定不得因發現鄰近問題而自行擴大需求；分析影響不等於取得修改權限。

### Commands and Verification

列出完成工作所需的 install、dev、lint、typecheck、test、build 或專案專用命令，並說明適用時機。無法執行時要求回報未驗證項目與原因。

### Git and External Actions

只有 repository 存在特殊流程時才加入。不得授予代理未由使用者提供的 commit、push、merge、PR、部署或外部寫入權限。

### Agent Collaboration

只有專案確實需要主代理與子代理分工時才加入。定義委派輸入、範圍、允許操作、證據格式與衝突整合方式；不要無條件要求使用子代理。

## 產生流程

1. 列出已查證來源與無法確認的項目。
2. 建立候選規則清單，為每項附上證據與收錄理由。
3. 排除全域偏好、通用知識、工具已強制內容、短期狀態與單次任務。
4. 依實際需要組成指令檔，不套用固定章節數。
5. 檢查路徑、命令、版本來源、作用域、優先順序與授權邊界。
6. 若獲得寫入授權，建立或更新目標檔案；否則只輸出完整草稿。
7. 寫入後重新讀取檔案，確認內容完整且沒有未替換 placeholder。

## 輸出要求

先交付完整、可直接使用的 `CLAUDE.md` 或 `AGENTS.md`，再附簡短產生報告。

產生報告必須包含：

| 項目 | 內容 |
| --- | --- |
| 已查證來源 | 實際讀取的檔案、設定與執行結果 |
| 收錄依據 | 各章節或重要規則所依據的 repository 證據 |
| 排除內容 | 未收錄項目及原因，例如屬於全域偏好或已有工具強制 |
| 待確認事項 | 證據不足、來源衝突或需要使用者決策的內容 |
| 驗證狀態 | 已執行與未執行的檢查，以及未執行原因 |

若使用者要求說明每個項目的參考依據，逐項對照正式內容，不得只提供整體理由。

## 完成前自我審閱

產出後按專案指令審閱標準自行檢查；若環境提供專門的審閱 skill，可用它檢查結果，但不得假設該 skill 必然存在。

- 每條重要規則是否有證據。
- 是否混入全域回答風格或個人偏好。
- 是否重複 manifest、README、formatter 或 linter 已充分管理的內容。
- 是否存在不可執行的絕對要求。
- 是否清楚區分事實、慣例、建議與待確認事項。
- 是否錯把分析責任寫成修改或 Git 授權。
- 主代理與子代理在沒有隱含對話背景時是否都能理解。

## 完成條件

- 產出的檔案可直接使用，沒有 placeholder 或虛構內容。
- 所有重要規則能追溯至已讀取來源或使用者明確要求。
- 內容以專案特有、可執行、可驗證且穩定的規則為主。
- 未確認內容沒有混入正式規則。
- 更新既有檔案時保留有效內容與使用者原意。
- 未超出使用者授權的修改、Git 或外部操作範圍。
