# 規格文件評分方法論

> **執行標準以 `agents/spec-scorer.md`（A/B 評分）與 `agents/spec-verifier.md`（C 差異驗證）為準。**
> 本檔只保留評分方法論（設計理由與流程說明），不重複執行規格——調整維度、權重或 checklist 時，修改 agent 定義即可，不需同步本檔。

---

## 方法論依據

評分維度與評分方法的設計來源：

| 方法論 | 核心概念 | 對應的評分維度/方法 |
|--------|---------|-------------------|
| IEEE 29148 | 需求品質屬性：correct, unambiguous, complete, consistent, verifiable, traceable | A 維度：完整性、準確性 |
| Specification by Example | 好的規格 = 可直接轉為測試案例 | B 可測試性評分；L2 驗收場景（GWT）章節 |
| BDD (Given-When-Then) | 行為導向、以使用者角度描述 | A 維度：完整性（行為覆蓋率）；B 行為盤點方式 |
| Architecture Decision Records | 決策記錄 why + trade-off | A 維度：Why 記錄 |
| Working Effectively with Legacy Code | 識別接縫、安全網思維 | A 維度：隱性規則覆蓋（風險識別） |
| Diátaxis | 不同目的的文件有不同品質標準 | 各層次權重矩陣的差異化設計 |
| C4 Model | 不同粒度給不同受眾 | A 維度：受眾適配 |

## 評分分工與流程

```
主 Agent（產出文件）
  ↓ Write 完成，依 SKILL.md「分層評分策略」決定本份文件的評分範圍
（需跑 C 時）啟動 spec-verifier —— 獨立盤點程式碼行為、比對覆蓋率
  ↓ 回傳覆蓋率 + 遺漏項 + 行為盤點數
啟動 spec-scorer —— A 多維度評分 + B 可測試性（L2）
  ↓ prompt 提供模板/規範的絕對路徑（scorer 自行讀取）與 C 盤點行為數
主 Agent（記錄到進度檔、判斷通過/補強/重做/人工介入）
```

### 為什麼拆成兩個 agent

C 差異驗證需要**獨立重讀程式碼盤點所有行為**——這是整個評分中最難的任務，用較弱的模型會偵測不足，因此 `spec-verifier` 不指定 model（繼承 session model）。A/B 是「讀文件打分」，`spec-scorer` 用 sonnet 即可，便宜的常跑、貴的少跑。

### 為什麼部分維度用 checklist 而非量表

LLM 評審對 1-5 量表的判斷不穩定（同一份文件重跑可能差 ±1 分，加權後總分浮動可達 ±8%，而 70 分及格線剛好落在雜訊範圍內）。對「有/沒有」的二元判準，判斷則高度可重現。因此可列舉的維度（格式規範、隱性規則的格式面）改為 checklist 通過率換分，只有真正需要整體判斷的維度（完整性、準確性、Why 記錄、受眾適配）保留量表。

### 為什麼 B 的分母要用 max(文件行為數, C 盤點數)

`可測試性 = 場景數 / 行為數` 的分母若由被評文件自己提供，文件可以靠「少寫行為」灌高分數（只寫 3 個行為但都很具體 → 100%，即使漏了 20 個行為）。C 驗證獨立盤點的行為數不受文件控制，取 max 之後漏洞關閉。未跑 C 的文件必須加註「未經 C 校準」，讓讀分數的人知道數字的邊界。

## 權重設計理由

| 層次 | 設計考量 |
|------|---------|
| **L0** | 給所有人看的鳥瞰圖，Why（為何這樣架構）和受眾適配最重要 |
| **L1** | 模組邊界需精確，完整性和準確性並重 |
| **L2** | ROI 最高的層次，隱性規則覆蓋是核心價值（QA 最怕踩到未記錄的地雷） |
| **L3** | API 契約需精確，準確性權重最高 |
| **L4** | 程式碼註解的核心是 Why，佔 30% |

權重矩陣的具體數值見 `agents/spec-scorer.md`。

## 修正流程細節

主 agent 收到評分結果後，依 SKILL.md「品質檢查與評分 › 執行順序」第 4 步處理。補強/重做時：

1. 從評分結果中識別**具體弱項**（哪個維度扣分、扣分原因；C 的遺漏項清單）
2. 回到原始碼重新驗證弱項相關的行為（**不憑記憶修正**——憑記憶修正只會複製第一次分析的盲點）
3. 更新規格文件中對應的段落
4. 啟動**新的** agent 重新評分（不可自我評分——自己修的自己評，confirmation bias 會讓分數失真）
5. 將**最終分數**記錄到進度檔（`docs/specs/spec-recovery-progress.md`）的對應表格（格式：`A:XX%` 或 `A:XX% B:XX%`；僅保留最終分數）
6. 若二次評分仍 < 70，使用 `AskUserQuestion` 請人工介入——連續補強無效通常代表缺少業務知識，不是分析技術問題
