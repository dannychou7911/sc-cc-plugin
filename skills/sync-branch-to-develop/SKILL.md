# 跨長期線同步開發分支

有些專案同時維護兩條長期線，例如 `master`（穩定線，對應正式環境）與 `develop`（整合線，對應測試環境）。功能在其中一條線的分支上開發完成後，另一條線也需要拿到同樣的變更。

**這件事只能用 cherry-pick 做。** 理由是兩條線本身就存在恆常差異——CI 設定、版號、環境參數、release 節奏造成的落差。這些差異是刻意的，屬於線本身，不屬於任何一個功能分支：

- 用 **merge** 會把整條來源線的差異灌進目標線，正式環境的設定就這樣跑進測試線。
- 用 **rebase** 同樣以來源線為基底重新套用，還會改寫 commit，讓兩邊再也對不起來。
- 用 **cherry-pick** 只搬該分支自己的那幾個 patch，目標線的既有狀態原封不動。這才是要的效果。

如果使用者要求改用 merge 或 rebase 來完成這件事，先說明上面的後果再請他確認——這通常是誤解，而不是真的想要。

## 先確認專案符合前提

這個 skill 只適用於**真的有兩條長期線**的專案。動手前先確認，不要假設分支叫什麼名字：

- 穩定線：依序找 `master`、`main`，取存在的那個。
- 整合線：依序找 `develop`、`dev`，取存在的那個。
- 兩者都要存在，且**不能指向同一個 commit**——如果完全同步，代表這個專案並沒有在維護兩條線，這個 skill 沒有用武之地，請告知使用者並停止。
- 若偵測到多個候選（例如 `master` 與 `main` 同時存在），停下來問使用者要用哪一條，不要自己猜。

`scripts/preflight.sh` 會自動做這些偵測，也接受明確指定。

## 命名規則

目標分支名 = `dev/` + 來源分支全名。

| 來源分支（穩定線基底） | 目標分支（整合線基底） |
| --- | --- |
| `feat/ABC-123` | `dev/feat/ABC-123` |
| `fix/ABC-456` | `dev/fix/ABC-456` |

`dev/` 前綴標示的是「基底是整合線」，不是分支類型，所以 `feat/`、`fix/` 的部分要完整保留。若專案用別的前綴慣例，先看 `git branch --list` 現有的分支怎麼命名，照既有慣例走。

方向也可能相反（從整合線的分支搬回穩定線）。流程完全一樣，只是把兩條線的角色對調，目標分支名改用該專案對應的慣例。

## 流程

### 步驟 0：前置檢查

執行本 skill 附帶的 `scripts/preflight.sh`。路徑用這個 skill 載入時提示的 base directory（訊息開頭的「Base directory for this skill」），不要猜測或寫死：

```bash
bash "<skill base directory>/scripts/preflight.sh" [來源分支] [穩定線] [整合線]
```

三個參數都可省略：來源分支預設為目前分支，兩條線會自動偵測。

它會一次回報：兩條線的偵測結果、working tree 是否乾淨、來源與目標分支狀態、分歧點、待搬的 commit 清單、是否含 merge commit，以及**兩條線之間現有的差異檔案**（這些就是最可能發生衝突的位置，讀一下能大幅加快後面的衝突判斷）。讀它的輸出再決定下一步，不要自己重跑一遍同樣的查詢。

遇到以下狀況**停下來問使用者**，不要自行決定：

- **找不到兩條線，或兩條線指向同一個 commit** — 前提不成立，說明原因並停止。
- **working tree 不乾淨** — 未 commit 的修改會跟著切分支跑。唯一的例外是與本次無關的 untracked 檔案，且目標分支上不存在同名路徑；這種情況說明清楚後可以繼續。
- **目標分支已存在** — 列出它已有的 commit、以及來源分支上還沒搬過去的部分，問使用者要續接、重建還是中止。絕不自行刪除重建，那會丟掉該分支上的獨立修改。
- **範圍內有 merge commit** — cherry-pick 一個 merge commit 需要 `-m` 指定保留哪一邊的父節點，選錯就會搬錯內容。請使用者確認該 merge 是否需要搬、或是否該先整理來源分支。

### 步驟 1：更新整合線

```bash
git fetch origin
git switch <整合線>
git merge --ff-only origin/<整合線>
```

用 `--ff-only` 而不是 `git pull`：如果本地整合線有分歧（有人誤在上面 commit 過），這裡會直接失敗並讓你看見，而不是默默產生一個 merge commit 汙染長期線。失敗時停下來回報，不要改用 `git pull` 或 rebase 繞過。

### 步驟 2：建立目標分支

```bash
git switch -c dev/<來源分支全名> <整合線>
```

明確寫出整合線當起點，不要依賴「目前在整合線上」的假設。

### 步驟 3：cherry-pick

用步驟 0 算出的分歧點：

```bash
BASE=$(git merge-base <穩定線> <來源分支>)
git cherry-pick $BASE..<來源分支>
```

用 merge-base 而不是直接寫穩定線名稱，是因為穩定線在這個分支開發期間可能已經往前推進；以分歧點為起點才能精準只拿到這個分支自己的 commit。

commit 數量多時可以逐一 cherry-pick，衝突時比較容易定位。範圍語法會依序套用，順序與原分支相同。

**衝突處理見下方「衝突」章節。** cherry-pick 中途的狀態是可以停下來的——不要為了讓指令跑完而猜測解法。

### 步驟 4：驗證內容無差異

這步不能跳過。cherry-pick 回報成功不代表內容正確——自動 merge 可能悄悄做出錯誤的合併，尤其在兩條線有差異的檔案上。

用兩個互相獨立的角度檢查，因為它們各自會漏掉不同的東西。

**角度一：`git range-diff`** — 把兩串 commit 一一配對，顯示每個 commit 的 patch 差在哪：

```bash
git range-diff --no-color --creation-factor=100 \
  $BASE..<來源分支> <整合線>..dev/<來源分支> | grep -E '^ *[0-9]+:'
```

先只看配對狀態列就能判斷整體是否乾淨。理想結果每列一個 `=`：

```
1:  4c4871c = 1:  a5a73d4 feat: 新增匯出報表功能
2:  e427183 = 2:  804754d fix: 修正匯出欄位順序
```

怎麼讀：

- `=` — 該 commit 的 patch 完全一致，理想狀態。
- `!` — 配對到了但 patch 有差異，拿掉 `grep` 展開看差在哪。解過衝突的 commit 出現 `!` 是正常的。
- `<` / `>` — **先不要當成搬漏**，見下方。

**為什麼要加 `--creation-factor=100`**：range-diff 靠相似度配對 commit，預設容忍度偏低。解衝突改寫過的 commit，patch 可能和原本差很多（例如整行 JSON 被改寫），相似度不足就會配對失敗，被列成 `<` 加一個空的 `-:`，看起來像「這個 commit 根本沒搬過去」——但它其實好好地在分支上。調高容忍度能讓它正確配對成 `!`。

所以看到 `<` / `>` 時，先確認是不是配對失效而非真的搬漏：

```bash
git log --oneline $BASE..<來源分支>
git log --oneline <整合線>..dev/<來源分支>
```

兩邊 commit 數量與訊息順序若一致，就是配對失效，不是搬漏。SHA 一定不同，那是 cherry-pick 的正常結果。

**角度二：樹狀內容比對** — 這個角度不受 commit 配對影響，是最可靠的判準：

```bash
git diff --stat <來源分支> dev/<來源分支>
```

結果應該**只剩下步驟 0 列出的那些線差檔案**。如果冒出功能相關的檔案，代表真的有搬漏或搬錯，要回頭查。反過來說，只要這裡乾淨，即使 range-diff 有 `!` 也多半只是解衝突造成的 patch 改寫。

**哪些差異是可接受的**：兩條線本來就有的差異可能讓某個 commit 出現 context 行不同，或讓解過衝突的 commit patch 內容改變。判斷標準是**最終改了什麼**，不是 diff 輸出長得一不一樣。

### 步驟 5：回報

告訴使用者：搬了幾個 commit、`range-diff` 的結論、樹狀比對是否只剩線差、以及有哪些差異屬於可接受的線差。

**不要自動 push**，除非使用者明確要求。把指令給他自己執行：

```bash
git push -u origin dev/<來源分支全名>
```

## 衝突

cherry-pick 停在衝突時，先搞清楚「為什麼衝突」再談怎麼解。這類專案的衝突絕大多數來自兩條線的既有差異——版號、CI 設定、環境參數，而不是真正的邏輯撞車。步驟 0 列出的差異檔案清單就是對照表。

向使用者說明衝突時要講清楚三件事，而不是只貼出衝突標記：

1. **哪個 commit、哪個檔案** — `git status` 列出 unmerged paths；目前套用到哪個 commit 看 `git rev-parse CHERRY_PICK_HEAD` 或 cherry-pick 的輸出。
2. **兩邊各是什麼** — 用 `git show <來源commit> -- <檔案>` 看這個 commit 原本想改什麼，用 `git show <整合線>:<檔案>` 看目標線現在是什麼。把「這個 commit 的意圖」和「目標線的現況」分開講，使用者才有辦法判斷。
3. **你的建議與理由** — 例如版號衝突通常應保留目標線的版號（版號屬於線差，不屬於這個 commit 的意圖），只把該 commit 真正要改的部分套上去。

給出建議後**等使用者確認**再動手改檔案。解完衝突：

```bash
git add <檔案>
git cherry-pick --continue --no-edit
```

加 `--no-edit` 是因為 `--continue` 預設會開啟編輯器讓你確認 commit message；在非互動環境下那會讓指令卡住不返回。沿用原訊息即可，不需要改寫。

需要放棄時用 `git cherry-pick --abort` 回到 cherry-pick 前的狀態——這會丟棄已解到一半的內容，執行前先問過使用者。

如果某個 commit 在目標線上其實不需要（它改的東西那邊已經有了），`git cherry-pick --skip` 可以跳過，但這會讓兩邊 commit 數量不一致，步驟 4 的驗證要明確說明為什麼跳過。

## 不要做的事

- **不要用 merge 或 rebase 代替 cherry-pick** — 會把兩條線的差異混在一起，這是本 skill 存在的理由。
- **不要 hardcode 分支名**，先偵測專案實際用的是 master 還是 main、develop 還是 dev。
- **不要 push**，除非使用者明確要求。
- **不要為了讓驗證通過而調整比對範圍**。range-diff 有差異就如實回報，讓使用者判斷。
- **不要動來源分支**。整個流程對來源分支是唯讀的。
