# Review Project Instructions

審閱專案級 `AGENTS.md` 或 `CLAUDE.md`。目標是讓主代理與子代理都能正確理解專案限制、採取一致行動，並避免規則檔變成教學文件、專案文件或單次任務清單。

## 執行邊界

- 預設只審閱與提出建議，不修改檔案；使用者明確要求修改或重寫時才可變更。
- 只根據已讀取的檔案、repository 設定與程式碼提出事實性判斷。
- 無法從現有內容確認的資訊標示為「待確認」，不得補成事實。
- 不得因審閱而順便修改程式碼、設定、依賴或文件。
- 若只取得節錄，明確限制結論適用於該節錄，不推論完整檔案。

## 必要輸入與探索

先讀取目標指令檔，再按規則涉及的範圍查證最小必要內容，例如：

- `package.json`、lockfile：命令、套件管理器與版本。
- framework、lint、format、test、build 設定：可執行命令與工具已強制的規則。
- 目錄結構與代表性檔案：架構、命名與實作慣例。
- 巢狀 `AGENTS.md`、`CLAUDE.md` 或同類規則檔：作用域與衝突。
- `README`、spec 或 architecture 文件：專案目的與已記錄的決策。

不要為了「完整探索」遍歷所有檔案。規則沒有涉及的區域不查。

## 審閱流程

### 1. 確認定位與作用域

判斷目標檔案是全 repository 規則或子目錄規則，並確認它應服務的代理與任務類型。找出上層、同層與下層規則，說明實際優先順序；工具本身的載入與覆蓋語意無法確認時，列為待確認。

### 2. 逐條分類

將每條規則歸入下列類型：

- 保留：專案特有、會改變代理決策且位置合理。
- 改寫：意圖必要，但內容模糊、不可執行、不可驗證或範圍不清。
- 移除：重複、空泛、可由程式碼直接得知、已由工具強制，或屬於通用知識。
- 移動：內容有價值，但應放在全域規則、子目錄規則、任務提示、spec、issue、README 或 `docs/`。
- 待確認：缺少證據，無法判斷真實性或適用邊界。

### 3. 套用審閱準則

逐條檢查：

1. 必要性：刪除後，代理是否更可能做出錯誤修改或錯誤判斷。
2. 專案性：是否真為本專案特有，而非通用程式設計常識。
3. 可執行性：是否明確告訴代理要做什麼或不得做什麼。
4. 作用域：是否指出適用目錄、檔案、任務或例外。
5. 可驗證性：是否可透過命令、測試、檔案或明確條件確認。
6. 正確性：路徑、命令、版本與架構描述是否符合 repository 現況。
7. 非重複性：是否與其他段落、工具設定或較高層規則重複。
8. 穩定性：是否容易因人員、排程、暫時狀態或單次任務而過期。
9. 強度合理性：`MUST` 是否只用於安全、相容性、架構邊界或明確不可違反事項。
10. 長度效益：內容成本是否低於它能避免的錯誤；能以連結取代的教學移至 `docs/`。

### 4. 檢查關鍵內容是否缺漏

只在 repository 確實需要時指出缺漏，不要求固定模板。常見關鍵內容包括：

- 專案目的與關鍵限制。
- 重要目錄、模組邊界與依賴方向。
- 修改禁止區、需先確認事項與禁止順手重構的邊界。
- 正確的 install、dev、lint、typecheck、test、build 命令。
- 專案特有慣例與例外。
- 完成條件，以及無法驗證時的回報方式。

### 5. 檢查主代理與子代理可用性

規則必須讓任一代理在沒有隱含對話背景時仍能執行：

- 避免「照之前方式」「相關檔案」「適當測試」等缺少指涉的表達。
- 需要協作時，寫清楚任務邊界、輸入、允許操作與回傳內容，不把是否使用子代理寫成無條件要求。
- 子代理只回報已查證結果、證據位置、未確認事項，不把推測包裝成結論。
- 主代理負責整合與衝突裁決；共享檔案可能同時修改時，規則應要求避免重疊寫入。

## 改寫規則

將抽象要求改成可觀察行為，並保留原意：

```md
<!-- 模糊 -->
- 注意程式碼品質。

<!-- 可執行 -->
- 新增 utility 前先搜尋既有實作；若建立新 utility，說明既有實作無法重用的原因。
```

補齊適用範圍與例外：

```md
- 新增 Vue 元件使用 `<script setup>`；修改既有 Options API 元件時，不得只為統一風格全面改寫。
```

完成條件使用 repository 內存在的命令，不虛構 script：

```md
完成前執行受影響測試與 `pnpm lint`。無法執行時，回報未驗證項目與原因。
```

## 輸出格式

先說結論，再提供證據。依問題數量調整細節，不為了套模板製造空段落。

### 總評

- 說明檔案目前是否可直接使用，以及最重要的 1～3 個問題。
- 區分「已查證事實」與「建議」。

### 審閱結果

有多項規則時使用表格：

| 位置／規則 | 分類 | 問題 | 證據 | 建議 |
| --- | --- | --- | --- | --- |

證據應包含實際檔案路徑、設定名稱或命令來源。只有行號穩定且有助定位時才附行號。

### 缺漏與衝突

只列會影響代理執行的缺漏、互相矛盾的規則，以及與 repository 現況不一致之處。

### 建議版本

使用者要求重寫時，提供完整可直接取代的 Markdown，不只提供零散片段。保留仍有效的原始規則，不任意加入個人偏好或新的架構決策。

### 驗證狀態

列出：

- 已讀取與查證的來源。
- 未執行或無法確認的項目及原因。
- 結論中仍屬推論的內容。

## 完成條件

- 每個重要判斷都有可追溯證據或明確標示為建議／待確認。
- 已指出不必要規則、模糊規則、錯誤資訊、重複內容與關鍵缺漏。
- 建議沒有超出專案既有決策與使用者授權。
- 若產出改寫版，內容可直接使用，且未虛構命令、路徑、版本或架構。
- 最終回覆清楚區分「規則內容問題」與「repository 本身問題」。
